# 流体适配体系审计报告

> 日期：2026-09-04 · 范围：`src/assets/styles/variables.css` 全量 + 全 `src/**/*.css` 的 clamp 消费
> 性质：**审计 / 分析**，不含落地改动。`src/` 未改动、未构建、未提交。
> 起因：用户质疑「`--layout-*` / `--avatar-*` / `--scrollbar-*` / `--header-height` 因倍数非 100 而本轮不动」这条规则的依据，并要求枚举项目全部流式适配机制。

---

## 0. 结论先行

**1）项目共 8 种流式适配机制并存**，其中 3 种正确、3 种有害、2 种是体系外游离。

**2）上一轮「倍数校验非 100 → 不动」的规则是错的，已作废。** 它把「真有独立契约」和「根本没有契约、系数随手填」混为一谈。用锚点反推一验就分开了：真正该「不动」的只有 **5 个** token，不是整个 `--layout-*` / `--avatar-*` / `--scrollbar-*` 大类。

**3）你说得对——恢复曲线解决不了问题，因为契约本身就是错的。** 契约是 `375→768`，意味着 **768px 以上全部冻结取 MAX**。14 寸（CSS 视口 1280）和 27 寸（2560）拿到完全相同的值。恢复曲线只是让这个错误设计「按预期运行」，大屏问题一动不动。

---

## 1. 审计方法：锚点反推法

上轮用的是「倍数校验」——拿 `(MAX-MIN)/393 × 100 ÷ 现写vw` 求倍数。这个方法**只能回答"是否符合 375→768 契约"**，无法回答"它自己的契约是什么"。

正确方法：任何一个 `clamp(MINpx, PREF + K·vw, MAXpx)` 都隐含一对锚点视口：

```
vw_lo = (MIN − PREF) ÷ (K/100)      // 触底视口
vw_hi = (MAX − PREF) ÷ (K/100)      // 触顶视口
```

解出 `(vw_lo, vw_hi)` 后看它落在哪：

- 落在 **375 → 768** 量级 → 移动段契约，正常
- 落在 **37400 → 76800** 量级 → 契约被整体放大 100 倍 → **漏写 100 的 bug**
- 落在 **600 → 2451** 量级 → 另一套真实契约，且实现正确
- `vw_lo = 0` 且 `vw_hi = 2000~16000`（非任何断点）→ **没有起点契约，K 是随手填的**

判据唯一、可复现，不依赖猜测。

### R1 — 375→768 契约流体（41 个）❌ 完全失效

范围：Typography 7 / Spacing 11 / Dots 4 / Component 6 / Switch 4 / Volume·Radio·Badge 5 / Radius·Gap 4（不含常量 `--text-base`）。

**契约证据（精确自洽）**：`--text-2xs` 的 `PREF = 0.4432rem × 16 = 7.0912`，而 `9 − 0.005089×375 = 7.0912` —— 分毫不差。证明作者确实按 `375→768` 设计，`K` 应为 `COEFF×100vw`，实际写成 `COEFF×1vw`。

**后果**：锚点被推到 37427→76643。现实视口内 clamp 恒取 MIN，拖到 3840 也不动一像素：

| token | MIN | MAX | 375 | 768 | 1280 | 1920 | 2560 | 3840 |
|---|---|---|---|---|---|---|---|---|
| `--space-lg` | 12 | 28 | 12 | 12 | 12 | 12 | 12 | **12** |
| `--grid-gap` | 12 | 24 | 12 | 12 | 12 | 12 | 12 | **12** |
| `--comp-btn-min-height` | 34 | 60 | 34 | 34 | 34 | 34 | 34 | **34** |
| `--text-2xl` | 20 | 24 | 20 | 20 | 20 | 20 | 20 | **20** |

### R2 — PREF=MIN 经验流体（46 个）⚠️ 无契约

特征：`PREF(rem×16)` 恰好等于 `MIN` → 反推 `vw_lo = 0`。即**没有"起点断点"**，从视口 0 就开始线性增长，`K` 是逐个手调的经验值。

**这就是为什么上轮把它们归为"另一套 regime"是错的**——它们不是"另一套设计"，是**没有设计**。

`K` 值实测：0.1 / 0.3 / 0.5 / 1 / 1.5 / 2 / 3 / 3.5 / 4 / 5 / 30…… 没有任何规律可言。

**后果**：同一个 3840 视口下，各 token 的行程完成度从 **0% 到 100%**，中位数仅 **28.5%**：

| 完成度 | 代表 token |
|---|---|
| 0% | `--error-msg-max-width`、`--layout-datepicker-width`、`--layout-hero-height-mobile`、`--layout-source-url-max-w` |
| 7% | `--layout-channel-num-w`、`--layout-select-w-mobile`、`--source-meta-min-width` |
| 28% | `--layout-tabbar-height`、`--layout-groups-collapsed-h` |
| 70% | `--layout-content-max-width`、`--avatar-xs` |
| 100% | `--layout-osd-max-width`、`--layout-select-w`、`--layout-spinner-border` |

视口变化时，这 46 个 token 以 46 种不同速率漂移，**彼此比例持续改变**。

### R3 — 真实独立契约流体（5 个）✅ 正确

**这才是唯一一批真正该「不动」的**：

| token | 行号 | MIN | MAX | 锚点 |
|---|---|---|---|---|
| `--layout-sidebar-width` | 272 | 260 | 320 | 379 → 3847 |
| `--layout-logo-size` | 297 | 48 | 64 | 612 → 2451 |
| `--layout-logo-size-sm` | 298 | 40 | 52 | 609 → 2253 |
| `--layout-logo-size-lg` | 299 | 56 | 72 | 610 → 2179 |
| `--header-height` | 337 | 60 | 76 | 600 → 2200 |

logo 三兄弟锚点收敛在 **609-612 → 2179-2451**，`header-height` 是 **600 → 2200** —— 高度一致，明显同一设计批次，且 `K` 是 `COEFF×100` 的正确形式。

**结论：真正该"本轮不动"的是这 5 个，不是整个大类。**

### R4 — TV 视口映射（61 个）✅ 正确

`variables.css:517` 有强制约定：TV 块内一律 `clamp(A, (A/19.2)vw, 2A)`。语义是「1920 取 A，3840 取 2A」，注释完整、实现正确、rem 基准也自洽（TV 下 rem 随视口 15→30px 流动，是"整条曲线 ×2"的实现手段，非 bug）。

### R5 — @media 阶梯断点（离散整数）⚠️

| 断点 | `--card-cols` | `--continue-cols` |
|---|---|---|
| 默认 | 3 | 2 |
| ≥768 (`:377`) | 5 | 3 |
| ≥1024 (`:386`) | 6 | — |
| ≥1280 (`:393`) | 8 | 6 |
| ≥2560 (`:411`) | 9 | 7 |
| ≥3840 (`:420`) | 10 | 8 |
| TV (`:657`) | **8（强制）** | 6 |

问题不在阶梯本身，而在**阶梯与流体混用**：尺寸连续变化、列数离散跳变，两者断点未对齐。

另有一处**实测断点跳变**：`--grid-gap` 在 `:404` 被 `@media(≥1920)` 覆盖为 `clamp(20px,1rem+0.5vw,36px)`，而 `<1920` 走 `:root` 的失效 clamp 恒 12px：

```
1919px → 12.00px
1920px → 23.60px     跳变 +96.7%
```

### R6 — 大屏兜底 2× 流体（6 个）✅ 正确

`variables.css:637-644`，`@media(≥1920) html:not([data-device="app"])`。

经查证**不是 TV 逻辑泄漏**：注释（`:630-636`）明确是「大屏覆盖，含 TV / 桌面 2K / 4K」，且 6 个消费点**全部**是 `max-height: min(Xvh, var(--layout-*-max-h))` 形式 —— 实际由 `vh` 主导，`max-h` 只是兜底上限（27 寸 1440 高时 `60vh=864px < 1466px`，vh 生效）。设计正确。

**但有 rem 偏差**：注释按 rem16 标注（如 EPG `576→1152px`），实际桌面 rem=14 → `504→1008px`。3840 时被截断在 1008，比设计值少 12.5%。

### R7 — 组件级硬编码 clamp（53 处）⚠️

分布在 11 个 CSS 文件（StillsLightbox 14 / Detail 8 / Person 8 / Home 4 / AppLoading 3 / UniversalPlayer 3 / 其余各 1-2），**完全脱离 token 体系**：

```css
/* Layout.css:3 */      --sidebar-width: clamp(160px, 12vw, 240px);
/* RecordShell.css:21 */ --record-aside-w: clamp(200px, 15vw, 260px);
/* StillsLightbox.css:37 */ width: clamp(2.5rem, 2rem + 1vw, 3rem);
```

这些**不受 `--ui-scale` 影响**，是任何全局缩放方案的盲区。

### R8 — 常量 + 派生（113 + 7）

- 常量 113 个：颜色 / z-index / 时长 / ease / 断点 / `--tap-target` / **`--text-base: 14px`**（`:160`）
- 派生 7 个：`--icon-*` = `calc(var(--text-*) × N)`（`:183-189`）

## 3. 上轮「倍数校验」规则错在哪

原规则：`(COEFF_375→768 × 100) ÷ 现写vw`，≈100 就修、≠100 就不动。

**缺陷**：`倍数 ≠ 100` 只能推出「它不符合 375→768 契约」，推不出「它是对的 / 别动」。它有两种可能：

- **(a) 另有正确契约** → 该不动
- **(b) 根本没有契约，K 随手填** → 这才是问题，需要重新设计

我上轮用倍数把这两种混为一谈，导致：

- **误伤**：`--layout-*` / `--avatar-*` / `--scrollbar-*` 里的 46 个其实属 (b)，是**需要重新设计**，不是「别动」
- **漏判**：真正属 (a) 的只有 5 个（R3），被淹没在大类里

修正后的边界：

| 原结论 | 修正后 |
|---|---|
| `--header-height` 不动 | ✅ 对（真契约 600→2200） |
| `--layout-logo-size*` 不动 | ✅ 对（真契约 609-612→2179-2451） |
| `--layout-*` 其余 41 个不动 | ❌ **错**，属 R2 无契约，需重新设计 |
| `--avatar-*` / `--scrollbar-*` 不动 | ❌ **错**，属 R2 无契约，需重新设计 |

## 4. 为什么「恢复曲线」不够 —— 原设计的 6 个错误

### 错误 1：桌面段零流体（根本错误）

契约 `375→768` 意味着 **768px 以上全部冻结取 MAX**。而桌面 CSS 视口跨度是 **1280 → 3840（3 倍）**，比移动段的 375→768（2 倍）还大，却**完全不响应**。

这就是「14 寸还行、27 寸不行」的设计层面根因 —— 恢复曲线后，两者**依然拿到完全相同的值**。

### 错误 2：`--text-base` 是常量，且不在流体体系内

`variables.css:160` → `--text-base: 14px`，同时 `index.css:258` → `html{font-size: var(--text-base)}`。它是整个字号体系的锚，**它恒定 = 排版体系恒定**。`--text-2xl` 就算恢复流体，base 不动，比例关系依然是死的。

### 错误 3：rem 基准分裂

| 环境 | rem 实际值 | 说明 |
|---|---|---|
| 桌面 | **14px**（恒定） | `--text-base: 14px` |
| TV | **15px → 30px**（流体） | `--text-base` 被重定义为 `clamp(0.9375rem,…)`，rem 解析用初始值 16px |

而**所有 clamp 的 PREF 都按 rem16 设计** → 桌面 PREF 实际偏小 **12.5%**。这是全局性的，R1/R2/R3/R6 全部中招。

### 错误 4：多套契约并存且锚点不一致

同一页面上 R1(375→768) / R3(600→2451) / R4(1920→3840) / R5(阶梯) / R6(1920→3840) 五种节奏同时跑，视口变化时各自按不同速率变化。

### 错误 5：R2 类 46 个 token 无契约

见 §2 R2，`K` 值手调、彼此无关，完成度 0%~100%。

### 错误 6：断点跳变未处理

`--grid-gap` 在 1919→1920 跳变 **+96.7%**（§2 R5）。

## 5. 重新设计：建议方案（**待拍板，未落地**）

### 核心分歧：桌面段要不要流体？

**不能全流体。** 硬限制：CSS 拿不到物理尺寸。27" 2560@100%（PPI 109）和 14" 1920@150%（PPI 157）的 **CSS 视口可能都是 1920、dpr 都是 1**，纯视口流体无法区分，必然误伤或漏网。

**也不能全冻结。** 那就是现状，正是问题本身。

### 建议：三段式

| 段 | 视口 | 机制 | 理由 |
|---|---|---|---|
| **移动段** | 375 → 768 | 流体 | 设备物理尺寸集中（5-7 寸），视口宽可靠反映物理尺寸 |
| **桌面段** | 768 → 1920 | **缓流体**（新增） | 此段差异主要来自窗口大小而非物理尺寸，流体合适 |
| **大屏段** | ≥ 1920 | **冻结 + `--ui-scale`** | 差异主要来自物理尺寸 / dpr，视口宽不可靠 → 交给显式缩放 |

这样 14 寸（CSS 1536）落在桌面段中间值、27 寸（2560）冻结 + 用户缩放，两者解耦。

### R2 类 46 个怎么归位

改为 `clamp(MIN, PREF + K·vw, MAX)` 契约 **375→1920**，`K = (MAX−MIN) ÷ (1920−375)`，1920 触顶后冻结。PREF 一律用 **px 字面**，消除 rem16/rem14 偏差。

### R1 类 41 个怎么归位

同上，契约改为 375→1920（不是恢复成 375→768）。

**`--text-base` 必须纳入流体**：改 `clamp(14px, …, 16px)` 契约 375→1920，否则字号体系锚死。

### R3 类 5 个：不动

已是正确的独立契约。

### R7 类 53 处：后续专项

不受任何 token 级缩放影响，需单独一轮收编（优先 Layout / RecordShell / StillsLightbox）。
