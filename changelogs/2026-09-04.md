## 2. 大屏观感调研（27 寸「分散」+ 字号偏小）— **仅调研与方案，未落地，待用户拍板**

- **用户真机反馈**（推翻第 1 项的部分假设）：27 寸显示器上「卡片排列布局看上去是合理的，但**文本、图标字体大小偏小**；把字体放大后**整体看上去很怪**；14 寸笔记本观感还可以，27 寸观感不好，感觉**内容很分散**」。

- **根因定位（按真实代码，非猜测）**：
  1. **基础 token 在 768px 就冻结**（`src/assets/styles/variables.css:146-152` 注释明确「坐近看屏…桌面不再随 4K 继续放大」）→ `--text-base: 14px`、`--space-*` 全档固定。**14 寸与 27 寸拿到的字号/间距完全相同**，差异不在代码。
  2. 差异在**系统缩放（devicePixelRatio）+ 观看距离**：14 寸笔记本 PPI≈157、Windows 默认 125%/150% 缩放（dpr 1.25/1.5）、观看距离 ~45cm；27 寸 2560×1440 PPI≈109、Windows 默认 **100%**（dpr=1）、观看距离 ~70cm。同样 14px 文字的**视角**差约 **1.4–1.6×**（14 寸 150% ≈ 0.43′ vs 27 寸 100% ≈ 0.27′ 量级）。→ 这就是「14 寸还行、27 寸偏小」的量化解释。
  3. **「放大字体很怪」的必然性**：`--space-*` / `--radius-*` / `--comp-*` / `--grid-gap` 是**独立 clamp、不随 font-size 走**。只放大 `--text-*` → 字号变大而字距/内边距/圆角/gap 全不动 → 文字撑破留白、比例失衡。**正解是全局等比缩放**（一个因子同时乘到全部 token），不是响应式放大字号。

- **「分散」的三处可指到行的来源**：
  | 来源 | 位置 | 现状 | 后果 |
  |---|---|---|---|
  | grid-gap 在大屏继续放大 | `variables.css:404` | ≥1920 覆盖 `clamp(20px,1rem+0.5vw,36px)` → 2560 时 ≈28.8px（比桌面 24px 大 20%） | 间距放大而文字不变 → 元素彼此越离越远 |
  | 列数在大屏越加越多 | `variables.css:409-425` | ≥2560→9 列、≥3840→10 列 | 卡片越碎，视觉重心涣散 |
  | 内容区锁窄、框架铺满 | `History.css:339-353`（第 1 项所加） | 2560 视口锁 1600px 居中，两侧各空 480px，而顶栏铺满 | 「孤岛感」 |

- **项目现状缺口（grep 实证）**：全项目 `src/` 内**无任何** `uiScale` / `devicePixelRatio` / `dppx` / `min-resolution` / `zoom:` 命中 → **完全没有 UI 缩放机制**。TV 的 `tvOverscan`（`useSettingsStore.ts:89`）只是安全边距滑块，不是缩放。

- **业界调研结论（主流视频/媒体站点共识，三件事组合）**：
  1. **卡片尺寸封顶**（Netflix ~250–310px、YouTube ~360px、B站 ~320px），**绝不**随视口无限拉伸；
  2. **列数随宽度增加（不是封顶）**——多出来的宽度用**更多列**消化，而非把卡片撑大（⚠️ 第 1 项的「封顶 5 列」方向与之相反，是放大问题而非解决）；
  3. **字号不随视口缩放，交给「用户显式 UI 缩放」**——YouTube（设置→外观→缩放 1x/1.25x/1.5x/1.75x/2x）、Plex/Jellyfin（`--scale-factor` / UI scale）、爱奇艺/腾讯（整站硬锁 1200–1600px）。响应式放大字号在所有产品里均被证明破坏比例。

- **建议落地路径（5 步，待拍板）**：
  1. `variables.css` 引入 `--ui-scale`，基础 token 定义统一包 `calc(clamp(…) * var(--ui-scale))`（`--icon-*` 派生自 `--text-*` 自动跟随，不重复缩放）；
  2. 自动档 `@media (min-width:1920px) and (resolution < 1.5dppx){--ui-scale:1.15}` / `@media (min-width:2560px) and (resolution < 1.5dppx){--ui-scale:1.3}` → 27 寸 100% 自动放大，14 寸 dpr≥1.5 的屏**完全不受影响**；
  3. 手动档：`useSettingsStore` 新增 `uiScale`（100/110/125/150%）写入 `<html>` 内联变量覆盖自动档（业界标准，最终拍板权在用户）；
  4. 网格改 `repeat(auto-fill, minmax(var(--card-max), 1fr))`，`--card-max ≈ 340px × --ui-scale`，列数自然推导，淘汰硬编码 9/10 列；
  5. 撤销 `variables.css:404` 的 gap 放大（或改跟随 `--ui-scale`）+ 放宽 History 内容区（1600 → ~1900px 或跟随缩放）。
  - **不使用** `html{zoom}` / `transform:scale()`：前者在 Chrome/Firefox 下对媒体查询、`vw/vh`、fixed/sticky 有一致性副作用；后者不影响布局流需额外补偿。项目已有完整 token 体系，`--ui-scale` 乘在 token 上最可控、零副作用，且 TV 模式「整条曲线 ×2」契约已验证可行性。

- **deliverable**：新增 `changelogs/demos/demo-large-screen-uiscale-2026-09-04.html`（复刻真实 token 与真实 RecordCard 结构，`--ui-scale=1` 时与线上 27 寸逐像素一致；四方案切换 + ui-scale/视口宽/内容区/列数/卡片封顶宽滑块 + 实时输出单卡宽/字号/gap/列数/两侧留白并按 PPI·dpr·距离换算**物理毫米与视角角分** + 业界对照表）；已在 `changelogs/README.md` 索引登记。

- **⚠️ 状态：未落地、等用户拍板两件事**——① 缩放幅度（滑块拖到 27 寸最舒服的值，预判 1.15–1.3，主观需用户定）；② 卡片尺寸路线（固定列数 vs 卡片封顶+列数自适应）。本轮**未改任何 `src/` 代码，未构建，未提交**。

## 【方案阶段 · 未落地】大屏 UI 适配详细设计方案（4 项决策已拍板）

- **用户决策**：① 全站一次铺开 ② 自动档 `≥1920px 且 dpr<1.5` ③ 手动档与自动档一起上 ④ 卡片宽度封顶 + 列数自适应、内容区 `max-width:2200px`；缩放幅度 **1.15**；首页横向行 **≥2560 由 9 列改 6 列**。

- **⚠️ P0 前置发现（第二期独立问题）——流体 token 体系实际失效**：`variables.css` 头注释公式 `clamp(MIN, PREF + COEFF·100vw, MAX)`，代码写成 `COEFF·1vw`（`--text-2xs` 的 `0.0051vw` 应为 `0.51vw`）→ **漏 100 倍** → 中项在 2560px 视口仍低于 MIN、甚至为负 → **clamp 恒取 MIN**。实测（rem=14px）：`--space-lg` 中项@2560 = −1.82 → 取 12px（设计 MAX 28px，仅 43%）；`--comp-btn-min-height` = 9.74 → 34px（设计 60px）；`--grid-gap` = 1.26 → 12px（设计 24px）。**桌面端从未拿到设计 MAX，一直取移动端最小值** —— 这是「27 寸文字偏小」的第二条真根因（与 dpr/距离并列）。
  - 影响：`--ui-scale` 乘 clamp 外层 → 放大的是 MIN 而非 MAX（`space-lg` 12×1.15=13.8px，仍是设计值 49%）。**1.15 是「在偏小基线上再放大 15%」**。
  - 处置：登记第二期，**本轮不动**。修 COEFF = 桌面间距 +133%、控件 +76%，剧变，须单独 demo。
  - 副产品：因 MIN 是硬编码 px，rem 14→16.1 只影响被截断的中项 → **不存在 rem 双重缩放**（已逐项核算）。

- **方案要点**（详见文档）：
  - `--card-size = calc(290px * var(--ui-scale))` = 333.5px；网格用 **`repeat(auto-fill, var(--card-size))` + `justify-content:center`**（固定轨道宽，单卡恒定不拉伸）——优于 `minmax(min,1fr)`（后者会把单卡拉伸到 405px/94.6mm）。
  - 内容区 `2200px` **硬上限、不随 scale 放大**（随 scale 则 2560 下可用宽被 padding 卡到 2468 → 单卡 388px/90.7mm 过大）。
  - 演算：1920→5 列 / 2560→6 / 3440→6 / 3840→6，**单卡恒 333.5px = 77.9mm**；2560 两侧留白 210px（现状 480，孤岛 −56%）。
  - 43 个 token 外层包 `calc(… * var(--ui-scale))`；`--icon-*` 派生自 `--text-*` 自动跟随不重复缩放；撤销 `variables.css:404` 的 gap 放大。
  - 手动档：`AppSettings.uiScale`（0=自动）→ `AppLayout` 写 `<html>` 内联 `--ui-scale`（内联优先于 `@media`，天然覆盖自动档）→ 设置页 AppearanceTab 档位 UI（仅非 TV 显示）。

- **TV 专项答复（用户提问）**：本方案**不适用于 TV，且不需适用** —— TV token 由 `[data-device="tv"]` 块（variables.css:510-618）独立重写为 `clamp(A,(A/19.2)vw,2A)`、不乘 `--ui-scale`；自动档显式 `:not([data-device="tv"])`。**唯一漏网**：新增的四条网格 `@media(≥1920)` 必须加 `html:not([data-device="tv"])` 前缀，否则会翻盘 `:656-660` 的 TV 恒 8 列。
  - 超大 TV 的真问题**不是字小**：占屏比恒 10.2%，98" 4K 的 30px 文字 @3m = 19.4′ > 55" 4K 的 10.9′；而是**卡片绝对尺寸失控**（98" 4K 单卡 22cm）。根因同桌面——CSS 拿不到物理尺寸（55"4K 与 98"4K 视口都是 3840、dpr 都是 1）。→ 第三期：TV 独立 `--tv-scale`（复用 `tvOverscan` 的 store→AppLayout→setProperty 通道）+ 列数按占屏比封顶（4K≈6 列）。

- **deliverable**：`changelogs/design-docs/2026-09-04-大屏UI适配方案.md`（决策记录 / P0 发现 / 43 token 改造清单含行号 / 6 处代码改动含完整代码片段 / 数值验证表 / 5 类风险与应对 / TV 专章 / 三期分期 / 落地顺序 11 步 / 回退方案 / 涉及文件清单）。

## 【审计阶段 · 未落地】流体适配体系全量审计（8 种 regime）

- **用户质询**：「不修的 --layout-* / --avatar-* / --scrollbar-* / --header-height 属另一套 regime（倍数 4–40 非 100）——这有什么逻辑？项目里到底有几种流式适配，全部列举并分析」。
- **审计方法（推翻上一轮「倍数校验」）**：对 `variables.css:37-374` 全部 92 个流体 clamp 做**锚点反推** —— `锚点 = (值 − PREF@rem16) ÷ (K/100)`，按隐含起止视口聚类，不再靠倍数猜。倍数法把「真有独立契约」和「没契约、系数随手填」混为一谈，**已作废**。

- **:root 内 92 个流体 token 分类（实测数值）**：
  - **R1 · 375→768 契约流体 ×41（❌ 完全失效）**：PREF 与 375→768 契约自洽，但 K 漏写 100 倍 → 反推锚点 37500→76800 → **clamp 恒取 MIN**。@2560 平均完成度 **0.0%**。
  - **R2 · PREF=MIN 经验流体 ×46（⚠️ 无契约）**：PREF 恒等于 MIN（`lo=0`），K 随手填，MAX/393 无关联。@3840 完成度 **24%~100% 离散 100pt**（中位 ~33%）——同一视口下各 token 行走速率完全无关联，纯拍脑袋。
  - **R3 · 真实独立契约流体 ×5（✅ 正确，本轮唯一不该动的）**：`--layout-sidebar-width`(379→3847) / `--layout-logo-size`(612→2451) / `--layout-logo-size-sm`(609→2253) / `--layout-logo-size-lg`(610→2179) / `--header-height`(600→2200)。锚点落在 600~3847，是真契约。
  - **修正上一轮结论**：「不动」的只有这 **5 个**，不是 `--layout-*`/`--avatar-*`/`--scrollbar-*` 整个大类——`--avatar-*` 实为 R2（无契约随手填）、`--scrollbar-*` 亦然。

- **:root 之外的 5 种机制（合计 8 种 regime）**：
