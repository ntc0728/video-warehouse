## 用户反馈 → 根因 → 修复

上一轮修复首页骨架时，我手工删掉了一个「已合并却仍留在 `_pending/`」的片段。用户要求根治
`scripts/changelog-collect.mjs`。隔离复现后确认是**两个独立缺陷**。

### 缺陷 1（严重）：已合并片段永不清除 → pre-push 永久阻断

```js
if (existsSync(archivedPath)) {
  console.log(`跳过(已归档): ${it.file}`);
  skipped++;
  continue;              // ← 只跳过，从不删 _pending/ 下的源文件
}
```

一旦某片段已在 `_archived/` 里（例如手工把归档拷回、或分支合并带回），它在 `_pending/`
下的残留就**永远清不掉**：每次运行都只打印「跳过(已归档)」，`_pending/*.md` 计数恒为 1，
而 `.git/hooks/pre-push` 正是以「`_pending/*.md` 数量 > 0」为阻断条件 → **push 永久被拒**，
且反复跑脚本无法自愈，只能人工 `rm`。

**修法**：命中「已合并」时，跳过合并但**把源片段移除**（`rmSync`）。若归档区缺文件则先补一份，
保证归档完整。

### 缺陷 2（数据正确性）：去重真源单一 → 归档丢失时重复追加

去重判据原本只有「`_archived/` 里有没有同名文件」。若 `_archived/` 丢失（换机 / 误删 /
分支未带过来），已合并过的正文会被**重复追加**进 changelog（实测同一段内容出现 2 次）。

**修法**：增加**正文级幂等兜底** —— 合并前用归一化后的正文（统一换行 / 去行尾空白 /
压缩连续空行 / 去首尾空白，不碰任何实质字符）判断目标 changelog 是否已含该片段；
命中则同样「跳过并清理 + 补归档」。

### 回归（隔离目录，5 场景）

| 场景 | 修前 | 修后 |
| --- | --- | --- |
| 正常合并 | ✅ | ✅ 合并 1 篇，`_pending` 清空 |
| 归档已存在 + `_pending` 残留 | ❌ **永久阻断 push** | ✅ 跳过并清理，`_pending`=0 |
| 归档丢失 + 重放同内容片段 | ❌ 正文重复 2 次 | ✅ 正文兜底拦下，仅 1 次，归档自动补回 |
| 不同片段（含高度相似 x/y） | — | ✅ 全合并，无误判 |
| `--dry-run` | ✅ | ✅ 不写文件 / 不删源 / 不建归档 |

边界：无 `_pending` 目录、`_pending` 为空、片段缺 `date` 字段（警告并**保留**待人工处理）均行为正确。
