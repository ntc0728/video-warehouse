大屏观感诊断 — 为什么 14 寸「还行」、27 寸「分散」

本页复刻项目真实 token 与真实卡片结构，--ui-scale=1 时与线上 27 寸屏逐像素一致。拖动滑块直接对比四种方案。

① 根因：你两台设备的「系统缩放」不同，CSS 像素不是物理尺寸

核心误解：项目的基础 token（--text-* / --space-* / --icon-*）在 768px 就冻结了（variables.css:146-152 明确写着「桌面不再随 4K 继续放大」）。 所以 14 寸笔记本和 27 寸显示器拿到的是完全相同的 14px 字号、完全相同的间距。差别不在代码，在系统缩放（devicePixelRatio）。
换算逻辑：浏览器里的 14px 是 CSS 像素，物理高度 = 14 × dpr ÷ PPI 英寸。 Windows 对高 PPI 笔记本默认给 125%/150% 缩放（dpr = 1.25/1.5），对 27 寸 2560×1440 默认给 100%（dpr = 1，PPI 仅 109）。 再叠加观看距离（笔记本 ~45cm vs 显示器 ~70cm），最终文字视角差出 1.4~1.6 倍 —— 这就是「14 寸还能看、27 寸偏小」的量化解释。

为什么「单独把字体放大」一定会怪

因为 --space-* / --radius-* / --comp-* / --grid-gap 是独立 clamp、不会跟着 font-size 走。 只放大字号 → 字变大、字距/卡片内边距/圆角/gap 全都不变 → 文字撑破留白、行挤成一团、卡片比例失衡。这就是你看到的「很怪」。 正解是全局等比缩放：一个 --ui-scale 同时乘到全部 token 上，比例恒定不变。

③ 主流产品怎么处理大屏（调研结论）

产品卡片尺寸列数字号内容区关键手段
Netflix 封顶 ~250–310px随宽度增加（最多 6–7） 固定 px无硬锁宽，靠列数消化 卡片绝不无限拉伸，多出来的宽度用更多列吸收
YouTube 封顶 ~360px随宽度增加 固定 + 用户可调缩放网格居中留白 设置 → 外观 → 缩放 1x/1.25x/1.5x/1.75x/2x
哔哩哔哩 封顶 ~320px随宽度增加 固定max-width ≈ 2200px 居中 首页提供「宽屏模式」开关
爱奇艺 / 腾讯视频 封顶随宽度增加 固定硬锁 1200–1600px（连导航一起） 整站锁宽成一条内容带，大屏就是留白
Plex / Jellyfin / Emby 用户可调自适应 固定 + UI scale跟随窗口 --scale-factor 1.25 / 设置项全局缩放
Disney+ / Max 封顶随宽度增加 固定居中留白 同上，卡片尺寸恒定
业界共识（三件事的组合，缺一不可）：
1. 卡片尺寸封顶 —— 卡片宽度有上限（280–360px），绝不随视口无限拉伸。这是解决「元素过大/过小」的根本手段。
2. 列数随宽度增加（不是封顶） —— 多出来的宽度用更多列消化，而不是把卡片撑大。你之前要求的「封顶 5 列」其实放大了问题：5 列 × 1600px = 单卡 320px，两侧还空 960px。
3. 字号不随视口缩放 —— 交给「用户显式缩放」 —— YouTube / Plex / VS Code / Slack / Discord 全都提供全局 UI 缩放设置，而不是响应式字号。响应式放大字号在所有产品里都被证明会破坏比例。
对照本项目现状，三个都对不上：
① 卡片宽度没有封顶 —— --card-cols 是硬编码列数（≥2560 → 9 列、≥3840 → 10 列，variables.css:409-425），卡片随视口被动拉伸/压缩，没有尺寸约束。
② 大屏把列数越加越多（9/10 列）→ 卡片越来越小、画面越来越碎 → 这就是「分散」的直接来源之一。
③ 完全没有 UI 缩放机制 —— 全项目 grep 无 uiScale、无 dppx/resolution 媒体查询、无 zoom、无 devicePixelRatio 检测。TV 的 tvOverscan 只是安全边距，不是缩放。

④ 建议落地路径（待你拍板）

步动作改什么解决什么风险
1 引入 --ui-scale 全局缩放因子 variables.css 基础 token 定义处统一包 calc(clamp(…) * var(--ui-scale))；--icon-* 派生自 --text-* 自动跟随，不重复缩放 一次缩放文字+间距+图标+圆角+控件，比例恒定 → 干掉「放大字体很怪」 中（一次性改 60+ token 定义）
2 自动档：按 dpr + 视口宽推断低密度大屏 @media (min-width:1920px) and (resolution < 1.5dppx) { --ui-scale: 1.15 }
@media (min-width:2560px) and (resolution < 1.5dppx) { --ui-scale: 1.3 }		 27 寸 100% 缩放（dpr=1）自动放大；14 寸 dpr≥1.5 的高 PPI 屏完全不受影响 低
3 手动档：设置页「界面缩放」档位 useSettingsStore 新增 uiScale（100/110/125/150%），写入 <html> 内联变量覆盖自动档 业界标准做法（YouTube/Plex/VSCode），最终拍板权在你 低
4 卡片宽度封顶，列数由容器推导 网格改 repeat(auto-fill, minmax(var(--card-max), 1fr))，--card-max 随 --ui-scale 缩放（≈340px×scale） 干掉「卡片无限拉伸」；列数自然确定，不再硬编码 9/10 列 中（影响所有卡片网格页）
5 撤销 ≥1920 的 gap 放大 + 放宽内容区 删除 variables.css:404 的 gap 覆盖（或让它跟随 --ui-scale）；History 内容区 1600 → 跟随缩放或放宽到 ~1900px 干掉「间距放大而内容不变」的失衡与孤岛感 低
为什么不用 html { zoom } / transform: scale()？ 前者在 Chrome/Firefox 下对媒体查询、vw/vh、fixed/sticky 定位有一致性副作用；后者不影响布局流，需要额外补偿宽高。 项目已有完整的 token 体系，--ui-scale 乘在 token 上是最可控、零副作用的路径，且 TV 模式早已用同一套「整条曲线 ×2」的契约验证过可行性。
需要你拍板的两件事：
1. 缩放幅度 —— 上面「全局等比缩放」滑块请拖到你 27 寸上最舒服的值（我预判 1.15–1.3，但这是主观的，只有你能定）。
2. 卡片尺寸路线 —— 是继续「固定列数 + 卡片随视口缩放」，还是改「卡片宽度封顶 + 列数自适应」（业界主流）。方案 D 可预览后者。
