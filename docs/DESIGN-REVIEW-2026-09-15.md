# KinoTV 三端设计规范审查报告（2026-09-15）

> **触发**：用户反馈「很多页面的文本看上去灰蒙蒙的，颜色设置得很奇怪，应该只有角标或类型标签才使用（这类低对比色/彩色）；项目里很多基础规范都没有」。
> **结论先行**：用户直觉成立且可量化——`--color-text-tertiary`（#999 / 暗色 #666）对比度仅 **2.85:1 / 2.87:1**，却以 `color:` 出现 **167 次**，是仅次于主文字的第三高频文字色，且被用于**承载信息**（榜单简介、设置项说明、时间戳）而非装饰。同时确认 6 项基础规范缺口（文字层级契约、字重/行高尺度、层级 z-index、动效时长、焦点可见性、触摸/安全区契约）。
> **方法**：① 全仓 CSS/TSX 静态统计（69 个 CSS + 343 个 TS/TSX）；② 按 WCAG 2.2 公式计算 token 对比度矩阵；③ Chromium 实测 8 组视口下的 token 解析值（Playwright，`data-device` 切换移动/Web/TV）。
> **未做的事**：本轮只读不改，未改动任何源码；未运行 axe 等自动化 a11y 扫描（环境内页面渲染受限），对比度为 token 级公式计算 + 用法静态盘点。

## 一、总体结论

| 维度 | 现状 | 评级 |
| --- | --- | --- |
| 尺寸/间距/响应式体系 | 流体 token + 三段式 + TV 独立 2× 契约，**行业上游水平** | ★★★★☆ |
| 端适配机制 | 移动/Web/TV/App 四态由 `data-device` + `data-mobile-layout` 统一驱动 | ★★★★☆ |
| 色彩体系（角色与对比度） | 三档灰 + 状态色**未与可访问性对齐**；硬编码色散落 | ★★☆☆☆ |
| 文本层级（语义与字号） | 无字重/行高 token；桌面段2 字号**逆视口递减**，档位塌缩 | ★★☆☆☆ |
| 交互基线（焦点/触摸/悬停） | **非 TV 全站移除键盘焦点环**；触摸目标未接线；hover 无触摸守卫 | ★★☆☆☆ |
| 基础规范文档化 | token 值有详尽注释，但**无对外可执行的规范基线文档 + 护栏规则** | ★★☆☆☆ |

**根因归纳（3 条）**

1. **文字层级只有「3 档灰」，其中最低档不达标却被当成通用色**。`tertiary #999` 在白色卡片上 2.85:1、在页面底色 #f5f5f5 上 2.61:1，低于 WCAG AA 正文要求的 4.5:1，甚至低于大字号/图形要求的 3.0:1。它被用于 `.chart-row__desc`、`.settings-menu-item__desc`、`.chart-head__sub` 等**信息性文字**——这就是「灰蒙蒙」的来源。
2. **彩色语义被挪用为装饰**。`.video-card-badge-item`（年份+类型徽标）背景固定 `--color-danger` 危险红、白字（3.76:1，小字号不达标）；`.video-card-status` 三种状态直接用硬编码 Tailwind 色 `rgba(59,130,246/.85)`、`rgba(217,119,6/.85)`、`rgba(34,197,94/.85)`，绕过 token 体系，暗色主题下不随主题适配。红色同时表示「危险/LIVE」「年份」「类型」「收藏」——**颜色语义过载**，与用户「颜色设置得很奇怪」的观察一致。
3. **字号契约与大屏可读性目标相悖**。段2（≥768）为「递减曲线」（2026-09-05 拍板，本报告不推翻其初衷，但从标准角度要求复核）：实测桌面 1920 正文 **13.00px**、次要 **12.00px**、辅助 **11.00px**，均**小于平板 768 的 14.00 / 13.67 / 12.67px**；2560 处 `--text-xs` 与 `--text-2xs` 同为 **11.88px**，两档语义完全塌缩。

## 三、问题清单

严重度：**P0** = 违反标准或直接损害可用性；**P1** = 明显偏离标准、影响体验；**P2** = 规范缺口/技术债。

### P0-1 文字最低档对比度不达标，且被用于承载信息（「灰蒙蒙」根因）

| 项 | 值 |
| --- | --- |
| 证据 | `variables.css:75` `--color-text-tertiary: #999`（暗色 `#666`，`variables.css:712`） |
| 实测对比度 | 浅色：**2.85:1**（白卡）/ **2.61:1**（页面底 #f5f5f5）；暗色：**2.87:1**（#1f1f1f 卡） |
| 用量 | `color:` 中使用 **167 次**（全项目第 2 高 token，仅次于 `--color-text` 196、与 `--color-primary` 165 同级） |
| 典型信息性用法 | `Chart.css:259 .chart-row__desc`（榜单简介）、`Chart.css:48 .chart-head__sub`、`Settings.css:772 .settings-menu-item__desc`（设置项说明）、`VideoCard.css:549 .video-card__time-inline`（时长） |
| 影响 | 榜单简介、设置说明、时长等信息在浅色主题下**不可读**（低视力/强光环境尤甚），是用户「灰蒙蒙」观感的直接来源 |

**建议**：把「3 档灰」重构为**语义 4 档 + 对比度契约**，并新增 `--color-text-disabled` 承接原先的「装饰性低对比」场景：

| 语义档 | 现取值 | 建议取值（浅色） | 对比度（白底 / 页面底） | 允许用途 |
| --- | --- | --- | --- | --- |
| `--color-text`（主） | `#000` | 不变 | 21.0 / 19.3 | 标题、正文、可点文本 |
| `--color-text-secondary`（次） | `#666` | 不变 | 5.74 / 5.27 | 次要信息、表单标签、时间戳 |
| `--color-text-tertiary`（辅助） | `#999` ❌ | **`#6b6b6b`** | **5.33 / 4.89** | 辅助说明、单位、补充信息（仍须 ≥4.5:1） |
| `--color-text-disabled`（禁用，新增） | — | `#bfbfbf` | 1.84（允许不达标） | **仅**禁用态、占位符、纯装饰图标 |

暗色侧：`--color-text-tertiary` 由 `#666`（2.87:1 ❌）→ **`#8c8c8c`**（4.90 / 5.48 ✅）；`secondary #a0a0a0`（6.30）保持不变。
落地口径：**「低对比灰」只允许出现在「禁用/占位/装饰」三类**——正面回应「只有角标或类型标签才该用」的直觉（角标可继续用彩色底，但文字对比度须按 P1-1 修正）。

### P0-2 非 TV 设备全站禁用键盘焦点指示（违反 WCAG 2.4.7）

```css
/* index.css:588 */
:root:not([data-device="tv"]) :focus-visible {
  outline: none !important;
  box-shadow: none !important;
}
```

- `:focus-visible` **只在键盘/辅助技术触发时命中**，对鼠标用户零影响；关掉它等于让键盘用户与「开关控制 / 语音输入 / 读屏+键盘」用户**完全失去位置感知**——这是 WCAG 2.4.7（AA）与 2.4.11 的硬性失败点。
- 连带后果：焦点环 token（`--focus-ring` `variables.css:278`、`--shadow-focus` `variables.css:136`）**几乎无人引用**（仅 `BackToTopButton.css` / `IPTVChannelCard.css` / `StatusTabs.css` 3 个组件），规范与实现脱节。
- TV 侧做得对（`[data-device="tv"] :focus-visible` 用 outline 3px + offset 2px，并规避了 overflow 裁切，`index.css:555-582`），说明团队已具备正确做法，非 TV 只是被一刀切屏蔽。

**建议**：非 TV 恢复 `:focus-visible` 焦点指示（复用 `--focus-ring` 双层环，或统一用 outline 保证不被裁切）；若担心历史「鼠标点击后残留焦点框」，`focus-visible` 本身已解决该问题，无需全局屏蔽。

### P0-3 桌面段2 字号逆视口递减 + 档位塌缩

实测（Playwright，`--text-*` token 渲染值）：

| 视口 | text-base | text-sm | text-xs | text-2xs | html font-size |
| --- | --- | --- | --- | --- | --- |
| 移动 390 | 14.00 | 13.03 | 12.03 | **9.05** | 14.00 |
| 平板 768 | 14.00 | 13.67 | 12.67 | 10.33 | 14.00 |
| 桌面 1024 | 13.70 | 13.12 | 12.16 | 10.45 | 13.70 |
| 桌面 1440 | 13.20 | 12.22 | 11.33 | 10.65 | 13.20 |
| 桌面 1920 | **13.00** | **12.00** | **11.00** | 10.87 | 13.00 |
| 桌面 2560 | 14.04 | 12.96 | **11.88** | **11.88** | 14.04 |
| TV 1080p | 15.00 | 14.00 | 13.00 | 11.00 | 15.00 |
| TV 4K | 30.00 | 28.00 | 26.00 | 22.00 | 30.00 |

- **逆递减**：1920 屏（最常见桌面分辨率）正文 13.00px < 平板 768 的 14.00px——**屏幕越大字越小**。
- **档位塌缩**：2560 处 `--text-xs` = `--text-2xs` = 11.88px（差值 0px）；1920 处仅差 0.13px。相邻语义档位失去区分度，token 命名失效。
- **低于行业下限**：Web 正文通行 16px（M3 body-large 16sp、国内主流 15–16px），19 英寸+ 显示器 13px 正文偏小；`--text-xs` 11px 已接近图标级。
- 与既有决策的关系：段2 递减为 **2026-09-05 用户拍板**（密度契约 v2.1，「段2 必须调小」），本报告不否定其密度初衷，但指出**缺少「可读性下限」保底**，建议改为 `clamp(下限, 递减曲线, 上限)` 形式，下限取 14/12/11（base/sm/xs）。

### P1-2 TV 端字号低于 10-foot UI 实践下限

- TV 1080p 基线 = 桌面冻结值：正文 **15px**、次要 14px、辅助 13px、角标 **11px**（`variables.css:792-799`）。
- 3m 视距下，11–15px 文字远低于 10-foot 通行建议（正文 ≥18sp，辅助 ≥16sp）与视角推导下限（≈21px）。
- TV 端还继承了暗色 `tertiary #666`（2.87:1），在远距离观看下更不可读。

**建议**：TV 块基线整体上调（正文 18–22px、次要 ≥16px、角标 ≥14px，4K 仍 2×），并同步复核 TV 布局（列数恒 8、卡宽、标题截断/跑马灯）——需 TV 实机或 1080p 模拟器回归。

### P1-3 TV rem 曲线的「文档值 vs 实测值」偏差（−6.25%）

TV 块用 `rem` 书写（如 `--header-height: clamp(4.75rem, 0.2474vw, 9.5rem)`），而 `html { font-size: var(--text-base) }` 在 TV 下 = **15px**（≠16px），于是「1rem 当作 16px 设计」的所有值整体缩水：

| token | 文档声称 | 实测（1080p / 4K） | 偏差 |
| --- | --- | --- | --- |
| `--header-height` | 76 → 152 | **71.25 → 142.50** | −6.25% |
| `--layout-logo-size` | 64 → 128 | 60 → 120（按同系数推算） | −6.25% |

同时 **桌面端 R3 契约「header-height 60→76」实际为 60 → 63.08（1920）→ 72.98（2560）**（`clamp(60px, 3.375rem + 1vw, 76px)`，`3.375rem` 随根字号 14→13px 缩水）。即：**头部高度契约从未真正命中上限**。

**建议**：需要「按 px 设计」的契约 token 一律改用 px 基准（与 `--text-base` 的 px 化修复同源，`variables.css:188-194` 已有先例），rem 仅用于确实要跟随根字号的场景；并把「R3 契约实测值」写入注释。
